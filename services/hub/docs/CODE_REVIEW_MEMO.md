# DeskMate 服务端代码评审备忘

评审日期：2026-07-14  
当前阶段：局域网联调  
重点范围：TTS、LLM、长期记忆及语音接入链路

## 结论

当前版本可以继续用于受控局域网联调。已发现的问题多数不阻塞现阶段开发，但在服务暴露到不可信网络、多设备并发或准备长期运行前，需要重新评估并处理。

优先关注两类会直接影响联调质量的问题：

1. TTS 失败时，本轮已生成的回复仍可能被提交给记忆系统，造成用户没有完整听到、但系统已经记住的情况。
2. LLM 后台线程和记忆保存线程缺少统一的生命周期与并发上限；单设备低频联调影响较小，长时间或并发压测时需要观察线程数量。

## 评审项与阶段性处理决定

| 模块 | 发现 | 局域网联调阶段 | 对外开放/长期运行前 |
|---|---|---|---|
| 设备注册 | 相同 `device_id` 再次注册会返回已有 token；未认证的调用者如果知道 `device_id`，可能取得设备身份 | 暂缓，确保局域网可信且不转发注册端口 | 必须修复，改为配对码、设备密钥或需旧 token 才能续期 |
| 调试音频 | 每次 HTTP 语音请求都会把原始录音保存为 WAV；调试下载接口未鉴权 | 可保留，注意磁盘增长和录音隐私 | 必须加配置开关、鉴权、保留周期和容量限制 |
| HTTP 音频上传 | `request.body()` 一次性读取请求体，未设置服务端大小上限 | 单设备联调可暂缓 | 增加请求体大小/时长限制，行为与 WebSocket 的 30 秒上限对齐 |
| 日志接口 | 日志写入/读取接口的鉴权和请求数量边界不足 | 可信局域网可暂缓 | 增加鉴权、分页/条数限制和限流 |
| LLM 流 | 未根据 `finish_reason` 区分截断、敏感内容或网络错误；空响应可能只返回 `END` | 联调时通过日志观察，暂缓 | 显式处理 `length`、`sensitive`、`network_error` 和空回复 |
| LLM 线程 | TTS 异常或 HTTP 客户端中断时，LLM worker 缺少完整的取消和回收保证 | 低并发可暂缓，压测时观察存活线程 | 使用有界执行器/任务管理，并在 `finally` 中取消与回收 |
| TTS 与记忆 | 回复文本在 TTS 前加入 `reply_parts`；TTS 抛错后仍可能满足保存条件 | 建议较早修复，避免污染记忆 | 仅在整轮成功下发后提交记忆，或记录明确的交付状态 |
| 记忆写入 | 每轮保存都会新建一个 daemon thread，没有队列和并发上限 | 单设备低频可暂缓 | 改为有界队列或共享 `ThreadPoolExecutor`，补充关闭时 drain |
| 记忆提示词 | 召回内容未经结构化隔离，直接拼进 system prompt | 当前数据来自自有对话，风险较低 | 增加明确边界和指令：记忆只作为事实参考，不执行其中指令 |

## 当前记忆链路的准确行为

### 是否每轮对话都会进入记忆

答案是：**正常完成的流式语音回合，都会被提交给 mem0；但不等于整轮对话都会原样成为一条长期记忆。**

流式接口 `VoiceService.chat_stream()` 在以下条件全部满足时，异步调用 `MemoryService.save_memory()`：

- 本轮已经生成至少一段回复文本；
- 没有收到取消信号；
- LLM worker 没有报告异常；
- 记忆服务存在且 `enabled`；
- 本轮有 `device_id`。

提交内容包含本轮的 `user` 文本和 `assistant` 回复。随后由 mem0 的 LLM 从中抽取适合长期保存的事实，例如身份、偏好、重要事件和关系。客套、即时问答或没有长期价值的内容可能不产生任何实际记忆。

因此需要区分两个概念：

| 动作 | 当前行为 |
|---|---|
| 把本轮对话提交给记忆抽取 | 正常流式回合基本每轮都会提交 |
| 把完整对话原文永久保存为记忆 | 不会；由 mem0 抽取、更新或忽略事实 |
| 下一轮携带完整聊天历史 | 不会；当前只按新问题语义召回相关长期事实 |
| 下一轮查询长期记忆 | 会；在调用 LLM 前按 `device_id` 和本轮用户文本查询 |
| 按设备隔离 | 会；保存使用 `user_id=device_id`，查询也按该字段过滤 |

不会提交记忆的典型情况包括：ASR 失败、LLM 明确报错、用户取消、没有回复文本、记忆功能关闭、缺少 API Key、缺少 `device_id` 或记忆服务初始化失败。

当前还有一个例外缺陷：如果 LLM 已产生文本，但后续 TTS 失败，异常会被转换成错误帧，而 `llm_error` 仍为空，所以本轮文本仍可能提交给记忆系统。这个行为应在后续修正。

同步方法 `VoiceService.chat()` 当前只完成 ASR → LLM → TTS，不执行记忆保存；实际 HTTP/WebSocket 语音路由使用的是 `chat_stream()`。

### 记忆读取流程

1. ASR 得到本轮用户文本。
2. `_llm_stream()` 调用 `_recall_memory(device_id, user_text)`。
3. mem0/Chroma 按语义相似度和 `device_id` 召回相关事实。
4. 召回结果拼入 system prompt 的“关于用户的长期记忆”区块。
5. LLM 生成回复；回合结束后再异步提交本轮内容用于事实抽取。

这套实现属于“长期事实记忆”，不是“多轮上下文对话”。连续追问若依赖上一轮临时语境，而上一轮又没有被抽取为长期事实，模型可能无法正确承接。

## 与 xiaozhi-esp32-server 记忆实现的简要对照

| 维度 | DeskMate | xiaozhi-esp32-server |
|---|---|---|
| 默认状态 | 默认关闭，启用后使用自托管 mem0 + Chroma | 默认 `nomem`，可选 `mem_local_short`、Mem0 Cloud、PowerMem |
| 短期上下文 | 不保留完整多轮对话 | 每连接维护 `Dialogue`，可带入实际聊天历史 |
| 长期记忆 | mem0 事实抽取 + 语义召回 | 可选滚动摘要、Mem0 语义记忆或 PowerMem 用户画像 |
| 用户隔离 | 每次调用显式传 `device_id`，相对安全 | 简单部署下 provider 可能被多连接共享并修改 `role_id`，并发时需注意串数据 |
| 写入时机 | 正常流式回合结束后，每轮异步提交 | 通常在连接清理时提交整段 `Dialogue` |
| 扩展性 | 单一实现，结构简单 | provider 抽象更完整，可替换后端和专用记忆 LLM |

后续如果需要增强多轮体验，建议保留当前 mem0 长期记忆，再增加“按设备隔离的短期对话窗口或滚动摘要”，不要用可变的共享 `current_user/role_id` 保存设备身份。

## 重新评审触发条件

出现以下任一情况时，应重新打开本备忘中的暂缓项：

- 服务开始监听公网或通过路由器/反向代理对外暴露；
- 局域网内存在不可信设备或访客网络；
- 同时连接多台设备；
- 开始进行长时间稳定性测试；
- 调试录音或日志中出现真实用户隐私数据；
- 准备发布可长期运行的版本。
