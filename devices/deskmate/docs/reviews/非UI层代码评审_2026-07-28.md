# DeskMate 非 UI 层代码评审报告

> 评审日期：2026-07-28
> 评审范围：Main / Application / Presentation / Service / Communication / Data / System / Device / BSP·Drivers·Boards / Product Protocols（**UI 层按要求不在本次范围**）
> 评审方法：分派 8 个并行子 agent，每层独立评审，按三项维度核查
> 基线文档：`README.md`、`AGENTS.md`、`docs/architecture/*`、`docs/时间校准流程.md`、`docs/低功耗流程.md`、`components/services/README.md`

## 评审维度

1. **文档符合度与偏移**（最高优先级）—— 对照 `layering.md` / `data_flow.md` / `api_conventions.md` / `c_cpp_boundary.md` 等已确认目标规范
2. **可删除/可裁剪代码** —— 死代码、过度封装、重复实现、占位接口
3. **功能可用性** —— 真实 Bug、并发竞态、资源泄漏、错误恢复

---

## 一、整体结论

除下述偏移外，各层总体遵守目标架构：Task 归属正确、公共 API 不泄漏 RTOS 句柄、C/C++ 边界清晰、产品策略基本未泄漏到 Communication/Device、`time_sync` 严守单次取样边界、低功耗与番茄钟流程实现与文档一致。

**最值得优先处理的三件事**：

1. **架构偏移**：BSP 长期 Task、System 吸收业务结构、System 越权做 SNTP 网络取样 —— 这三项是文档明确点名的"待迁移项"，持续累积会让后续迁移更难。
2. **真实功能 Bug**：I2C 总线并发、`protocol_identity_add_headers` 越界风险、`pomodoro_store` 非原子、语音 FAILED 永久不睡眠 —— 会在实机偶发触发。
3. **死代码清理**：`log_upload.*`、`bsp_i2c` 读写包装、RGB565 路径、`memory_stats_timer` 等零风险高收益项，可安全删除。

## 二、高严重度问题（建议优先处理）

### 架构偏移类

#### H1. BSP 内置长期刷新 Task，违反 Device/BSP 执行边界

`bsp_display.c` 创建永久 `while(true)` 的 `display_flush_task`，属"产品持续流程执行资源"。

- 位置：`components/bsp/src/bsp_display.c:1109-1176`（任务体）、`:1343-1349`（创建）、`:1651`（删除）
- 依据：`docs/architecture/layering.md`「硬件边界」—— "BSP 可以提供 ISR 或 SDK 回调入口，但**不得为产品持续流程创建或管理 FreeRTOS Task**"；「DMA/TE 短期传输」—— "若实现需要长期 Task，应将执行资源上移到 Service，BSP 只保留有界传输和完成通知"；`docs/architecture/data_flow.md`—— "Device/BSP 不得创建长期 Task"。
- 建议：刷新队列消费 Task 应上移到 Service（或 Device Display 的私有执行资源），BSP 只暴露"提交一帧 + 等待 DMA 完成"的有界同步/异步契约。`_task.c` 命名规则也要同步迁移。

#### H2. System 仍在吸收业务结构，且部分是活跃 API

`system_storage.h` 暴露 `system_storage_network_config_t`、`system_storage_daily_alarm_t`、`time_synced`、`ota_display_restore_pending` 等业务结构；网络配置经 `settings_store.c` 双写持续注入 System。

- 位置：`components/sys/include/system_storage.h:24-40`、`components/sys/system_storage.c:19-29,124-323`；`components/sys/settings_store.c:56-71`
- 依据：`docs/architecture/layering.md`「业务持久化边界」—— "产生业务状态的组件拥有该状态的持久化结构、版本、兼容与迁移语义；System/Data 只提供键值、Blob、文件、事务或缓存机制"；`docs/architecture/README.md`「当前迁移说明第 6 条」—— "`components/sys/system_storage.*` 中保留的部分业务结构属于**待迁移实现**，不作为后续组件继续向 System 增加业务结构的依据"。
- 建议：把 `device_settings_t`（含网络字段与 OTA 产品策略）整体上移到 `main/application/app_settings`，让 Application 通过通用 NVS 键值 API 自己声明键；`settings_store` 与 `system_storage` 中的网络/告警/OTA 产品结构都属裁剪候选。

#### H3. `system_clock_sync_from_sntp()` 把 SNTP 网络取样拉进 System

`system_clock.c` 直接调用 Communication 的 `time_sync_sample_sntp_once_copy()` 并管理取样循环（最多两个样本的二次确认策略），令 System 反向依赖 Communication。

- 位置：`components/sys/system_clock.c:677-761`、声明于 `components/sys/include/system_clock.h:120-132`
- 依据：`docs/architecture/layering.md`—— "SNTP 的单次网络取样属于 Communication，候选接受、可信锚点与 RTC 回写仍属于 System"；`docs/时间校准流程.md` 第 4-5 条把"调用共享 time_sync 请求样本"放在 `app_network`。
- 建议：System 只暴露 `system_clock_set_time()`（候选接受锚点 + RTC 回写）；取样循环上移到 `app_network` 调用 `time_sync_sample_sntp_once_copy()`，再把候选 `system_clock_set_time()`。

### 功能 Bug 类

#### H4. 共享 I2C 总线无总线级并发保护

`bsp_i2c.c` 的 `s_bus_mutex` 只保护了死路径 `bsp_i2c_write/read/write_read`；真正活跃的客户端（RTC、SHTC3、Codec）全部直接调 ESP-IDF `i2c_master_*`，完全没有取 `s_bus_mutex`。`bsp_rtc.c` 只用自己的 per-外设 `s_mutex`，无法串行化跨外设的同一总线。

- 位置：`components/bsp/src/bsp_i2c.c:166,196,227`（mutex 仅在死路径 take）；`components/bsp/src/bsp_rtc.c:43-46,326-328`（RTC 锁是设备级而非总线级）；`components/bsp/src/bsp_environment.c:67-68`（无锁）；`components/bsp/src/bsp_audio.c:551-586`（无锁）
- 影响：`environment_service` 与 RTC alarm/INT 恢复逻辑并发时，SHTC3 测量序列和 PCF85063 读改写（AF/TF 清零尤其敏感）可能交错，出现偶发 I2C 错误或告警标志被错误清零。
- 建议：让 BSP 把 `s_bus_mutex` 下推给所有真实客户端，或让所有 driver 接受一个共享锁回调。

#### H5. `protocol_identity_add_headers` 缺容量参数，所有调用方缓冲正好填满

函数原型无 capacity 入参，直接 `headers[(*count)++] = ...`。当前所有调用方缓冲恰好填满无余量。

- 位置：`shared/components/communication/protocols/src/protocol_identity.c:37-55`
- 调用方：`log_upload.c:30 headers[3]`、`deskmate_api.c:45 headers[3]`、`voice_service.c:518 headers[4]`、`device_status_protocol.c:78 headers[4]`、`display_protocol.c:277/379` —— 都从某起始 count 填到恰好满。
- 影响：任一调用方起始 count 改大或新增一种身份头，就是栈越界写入。
- 建议：加入 `capacity` 参数，或在 Doxygen 中固化"调用方数组容量必须 ≥ *count + 2"的硬约束。

#### H6. `pomodoro_store_save_counts()` 非原子却宣称"原子提交"

三个独立 `nvs_set_*` + 一个 `nvs_commit`，NVS 的 commit 只保证"本句柄的待写刷盘"，不保证多键事务原子性。

- 位置：`components/data/pomodoro_store/src/pomodoro_store.c:131-154`、声明于 `pomodoro_store.h:69-76`（"原子提交今日日期、今日完成数和未定日完成数"）
- 影响：掉电可能命中 `today_date` 已写而 `today_count` 未写，下次启动今日完成数与日期错配。文档要求"断电不丢"。
- 建议：把三项合并成一个 blob；或显式接受非原子（删除头文件"原子提交"措辞）。

#### H7. `app_power` 启动失败回滚不完整，泄漏语音 Runtime

`app_main.c` 在 `app_power_start` / `button_service_start` 失败分支只回滚 UI Runtime，未回滚已成功启动的 `app_voice` Runtime 及其依赖（audio_service、audio_processor_service、device_audio）。

- 位置：`main/app_main.c:591-616`
- 影响：启动失败后语音 Task 与音频资源残留。
- 建议：失败分支补齐 `rollback_voice_runtime()` 及其下层依赖回滚。

#### H8. 语音 FAILED 态导致设备永久无法自动睡眠

`app_power_task.c` 把 `APP_VOICE_STATE_FAILED` 当成可重试阻塞条件（设 `BLOCKER_VOICE`），但 FAILED 是粘性态（`app_voice_start` 要求 STOPPED，无产品路径清除）。

- 位置：`main/application/app_power_task.c:158-162`；结合 `app_voice.c:245-254`（start 要求 STOPPED）、`app_voice.c:490-498`（consume_input 要求 RUNNING）
- 影响：一次语音生命周期失败后 Power Task 永远返回带 BLOCKER_VOICE 的循环（仅按 `retry_delay_ms` 唤醒重试，永不睡眠），直到设备重启。
- 依据：`docs/低功耗流程.md`「活动录音、上传、播放、AFE drain 是暂时睡眠阻止条件」—— FAILED 不在列。
- 建议：要么将 FAILED 视为"无法安全停止/恢复"走 `enter_blocked`（与文档一致），要么在 `app_voice` 提供 FAILED → STOPPED 的产品级恢复入口（周期自愈或按键自愈）。

#### H9. Main 层承载产品决策，偏离 Composition Root 职责

`app_main_start()` 直接调 `firmware_ota_confirm_running_image()`（OTA 时机）、`app_page_publish_initial_ui()`（页面派发）、`app_network_set_dashboard_auto_sync_enabled(true)` + `app_network_request_sync()`（Dashboard 同步时机）。

- 位置：`main/app_main.c:578-589`（页面）、`:618-622`（OTA）、`:624-633`（Dashboard 同步）
- 依据：`docs/architecture/layering.md`—— "Main 不得包含页面切换、网络重试、OTA 时机、语音策略或环境采样周期等运行期产品决策，也不得成为永久业务循环"。
- 建议：把这些产品决策下放到对应 Application（`app_ota` / `app_page` / `app_network`）。

#### H10. `home_presenter` 的 `s_env_view` 跨 Task 读写无锁

环境 Service 事件回调（默认 event loop Task）写入 `s_env_view`，UI Runtime Task 读取，构成整结构撕裂竞争。

- 位置：`main/presentation/home_presenter.c:18,76-80,108`
- 影响：温湿度/状态字段偶发显示错乱。
- 依据：README §6 只承诺了 `status_bar_presenter` 的锁，未覆盖 home。
- 建议：加 `portMUX_TYPE` 短临界区，或参照 `status_bar_presenter` 模式。

#### H11. `system_filesystem_init()` 在 `FR_INT_ERR` 时自动格式化清空整卡

`FR_INT_ERR`（FatFs 内部错误）可能由瞬时读写故障、电源跌落、卡拔引起，触发自动格式化会清除用户数据。

- 位置：`components/sys/system_filesystem.c:294-312`、声明于 `include/system_filesystem.h:35-41`
- 建议：自动格式化只在初始化路径的 `FR_NO_FILESYSTEM` 触发；`FR_INT_ERR` 返回错误让 Application 决定是否格式化。
