# `provisioning_app`

> 网络可用前的 Application 用例，负责把网络状态收敛为配网页面或正常页面入口。

## 1. 定位

- 层级：Application
- 触发方：Main / Composition Root 在持久化、显示和网络管理能力初始化后同步调用
- 主要输出：需要用户处理网络时展示配网二维码并维持三分钟无交互窗口；获得可用 IPv4 后
  清除二维码并返回 `ESP_OK`，无人值守的启动失败收敛到定时深睡

## 2. 职责边界

负责：

- 启动一轮 `network_manager` 会话并在变化通知后读取一致的状态元数据。
- 普通冷启动或任意按键唤醒且无有效网络配置时请求启动配网 Portal。
- 将 Portal 提供的 Wi-Fi 二维码居中绘制并提交到墨水屏。
- 本轮曾展示二维码时，在网络可用后清除二维码并把执行权交还给正常页面流程。
- Portal 连续三分钟没有真实用户活动时保留当前画面，进入仅按键可唤醒的深睡；打开页面、
  点击、滚动、输入、提交和候选配置验证失败都会重置窗口，自动扫描和状态轮询不会重置。
- 已保存配置在定时唤醒中连接失败时，按 RTC 内连续失败次数进入 1/5/15 分钟定时深睡
  重试，后续连续失败按一小时封顶。
- 任意按键唤醒且已保存配置连接失败时，保留旧配置并进入可修复的 Portal。

不负责：

- Wi-Fi Driver、会话内重连、Portal HTTP 服务、候选配置验证和持久化事务，这些由
  Communication/System 组件负责。
- 联网后的内容下载、正常页面布局和定时刷新策略。
- 解释 ESP-IDF 原始断开原因；本组件只消费 `network_manager` 状态对应的 `esp_err_t`。

## 3. 主要流程

```text
Main 调用
    ↓
启动 network_manager 并等待状态通知
    ├── 无配置或有维修意图 → 请求 Portal → 显示二维码
    │                               ├── 真实活动 → 三分钟窗口重新计时
    │                               ├── 提交候选配置 → Portal 保持在线并验证
    │                               │                    ├── 失败 → 回到表单并重新计时
    │                               │                    └── 获得 IPv4 → 提交配置并关闭 Portal
    │                               └── 连续三分钟无交互 → 仅按键唤醒的深睡
    ├── ONLINE → 若显示过二维码则清屏 → 返回 ESP_OK
    └── 定时唤醒连接失败 → 停止网络 → 1/5/15 分钟、随后一小时封顶的定时深睡
```

`network_manager` 回调只向调用者 Task 发送通知；状态读取、控制命令、二维码生成和最长约
15 秒的墨水屏刷新均在调用者 Task 中执行。

## 4. 依赖关系

| 方向 | 组件 | 用途 |
| --- | --- | --- |
| 调用 | `network_manager` | 启动网络会话、读取状态和请求 Portal |
| 调用 | `connect` | 把 Portal Wi-Fi payload 转换为显示格式无关的二维码矩形 |
| 调用 | `device_display` | 写入内部帧并同步刷新墨水屏 |
| 调用 | `power_management_app` | 复用启动阶段有序停机和跨深睡失败退避 |
| 被调用 | `main` | 初始化下层依赖并运行完整配网用例 |

依赖只出现在私有实现中；公共头文件仅依赖 `esp_err_t`。

## 5. 公共接口

公共头文件：[`include/provisioning_app.h`](include/provisioning_app.h)

| API | 同步性 | 作用与完成语义 |
| --- | --- | --- |
| `provisioning_app_run_until_online(config)` | 同步阻塞 | 根据按键/定时器唤醒来源选择交互修复或无人值守退避；返回 `ESP_OK` 时网络已获得 IPv4，成功进入深睡时不返回 |

## 6. 状态、生命周期与并发

- 生命周期：单次同步用例；调用前由 Composition Root 初始化所有下层组件。
- 状态所有者：Portal 是否已请求、二维码是否已显示、活动序号和三分钟截止时间均为本次调用的
  栈内状态，由调用者 Task 唯一写入。
- Task：本组件不创建 Task，使用调用者 Task 等待通知和执行显示操作。
- 回调/队列：变化通知回调运行于 `network_manager_task`，只使用 Task Notification 唤醒调用者；
  组件不创建队列。

## 7. 故障与恢复

- 二维码生成、显示刷新或网络状态出现不可收敛错误时，函数解除变化通知回调借用并尝试停止本轮
  网络会话，然后向调用方返回原始错误。
- 参数校验和无需清理的同步调用直接传播原始 `esp_err_t`；进入网络会话后的错误保持显式收敛，
  解除回调或停止会话的附加失败不覆盖本轮主错误。
- Portal 候选配置验证失败时保持配网页面和原有 active 配置，展示稳定错误提示并等待再次提交。
- 二维码首次显示后使用单调 Tick 计算三分钟截止时间；`portal_activity_sequence` 变化时重新计算。
  截止瞬间会复读最新状态，避免临界时刻的活动被休眠竞态吞掉。
- 已保存配置的单轮重试由 `network_manager` 管理；耗尽后交给 `power_management_app` 使用 RTC
  保留的 1/5/15 分钟失败退避，连续失败再按一小时封顶。任意按键表达用户在场意图，因此该次
  启动失败会转入 Portal；定时器唤醒不主动展示 Portal。

## 8. 配置与文件

- 构建配置：复用 `connect` 和 `network_manager` 的现有 Wi-Fi/Portal 配置。
- 产品参数：Portal 无真实用户活动窗口固定为 180000 毫秒。
- `src/provisioning_app.c`：同步用例、状态通知和二维码到显示矩形的适配。
- 持久化格式：本组件不拥有持久化数据。

## 9. 验证

- 静态核查：公共 C ABI、依赖方向、回调上下文和显示串行调用。
- 实机检查：清空网络配置后应显示可扫码二维码；真实交互应重置三分钟窗口，自动轮询不得
  重置；错误密码或不可用 AP 应保持 Portal 和旧配置并允许再次提交；候选配置获得 IPv4 后才
  写入并进入正常页面；三分钟无交互应保留二维码深睡；定时唤醒时关闭已保存配置对应的 AP
  应按 1/5/15 分钟、随后一小时封顶重试，任意按键唤醒则进入修复 Portal。
- 已知缺口：当前没有自动化测试覆盖 Portal、真实 Wi-Fi 事件和墨水屏刷新组合流程。
