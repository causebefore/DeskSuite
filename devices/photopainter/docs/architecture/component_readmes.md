
# Application 与 Service 组件 README 规范

> 本文规定 `components/application/<component>/README.md` 与
> `components/services/<component>/README.md` 的创建、内容和维护方式。组件 README
> 只描述该组件已经实现或已经确认的契约；全项目架构仍以本目录其他规范为准。

## 1. 目的与适用范围

组件 README 用于让维护者在阅读实现前回答以下问题：

- 组件为什么存在，属于 Application 还是 Service。
- 组件负责什么，明确不负责什么。
- 谁触发它、它调用谁、结果返回给谁。
- 它拥有哪些状态、Task、回调或共享资源。
- 生命周期、失败终态和降级边界是什么。

以下目录中的每个项目自有 ESP-IDF 组件都必须有自己的 `README.md`：

```text
components/application/<component>/README.md
components/services/<component>/README.md
```

`components/services/README.md` 等层级 README 描述整层规则，不能代替具体组件 README。
第三方组件、`managed_components`、生成目录以及不属于 Application/Service 的组件不在本文
强制范围内。

## 2. 创建与更新时机

- 新建 Application 或 Service 组件时，必须在同一任务、同一提交中创建 README。
- 实质修改组件职责、公共 API、依赖方向、生命周期、状态所有权、Task、回调、主要数据流、
  故障恢复或构建开关时，必须在同一任务中同步更新 README。
- 仅格式化、改正拼写或进行不改变契约的私有重构时，应检查 README 是否仍准确；内容无变化
  时不为制造改动而改写。
- 既有组件尚无 README 时，Agent 在首次实质修改该组件时必须补齐；不得一次性生成缺少事实
  依据的空壳文档。

README 是组件级导航和契约摘要，不替代公共头文件中的精确 API 契约、Doxygen 注释、测试或
架构规范。发现实现与目标架构不一致时，应明确写成“当前实现偏移”或单独报告，不得把偏移
包装成新的架构规则。

## 3. 编写原则

- 使用简体中文和 UTF-8；函数、类型、配置项、文件名及错误码保留原文。
- 先写职责边界和数据流，再写文件列表；不得只把目录树当作 README。
- 只记录当前代码和已确认规范能够证明的事实。规范列为未决的内容必须写“未定义”或省略，
  不得由 Agent 自行决定。
- 使用相对链接指向公共头文件、相关架构规范和测试，不复制大段源码或 Doxygen 内容。
- API 表只列对理解组件有帮助的公共入口；完整签名和参数契约以公共头文件为准。
- 小组件可以压缩“不适用”的章节，但不得删除“定位”“职责边界”“主要流程”“依赖关系”
  和“验证”五个核心章节。
- 只有流程包含至少三个关键阶段、分支或异步回传时才使用 Mermaid 或文本流程图。

## 4. 通用 README 模板

新组件从以下模板开始，并删除方括号说明。标题必须与 ESP-IDF 组件名一致。

````markdown
# `<component_name>`

> 一句话说明组件所属层级、解决的问题和核心边界。

## 1. 定位

- 层级：Application / Service
- 触发方：[谁启动或调用该组件]
- 主要输出：[结果、事件或产生的持久化状态]

## 2. 职责边界

负责：

- [职责一]
- [职责二]

不负责：

- [明确留给上层或下层的决策/机制]
- [容易被误放进本组件的职责]

## 3. 主要流程

```text
[输入或触发]
    ↓
[关键调用或状态转换]
    ↓
[结果返回、事件通知或提交点]
```

## 4. 依赖关系

| 方向 | 组件 | 用途 |
| --- | --- | --- |
| 调用 | `<dependency>` | [使用的稳定能力] |
| 被调用 | `<consumer>` | [调用场景；未知时写“由目标 Application 装配”] |

说明公开依赖与私有实现依赖，以及可选依赖不可用时的行为。不得把 CMake 列表不加解释地复制
到这里。

## 5. 公共接口

公共头文件：[`include/<component_name>.h`](include/<component_name>.h)

| API | 同步性 | 作用与完成语义 |
| --- | --- | --- |
| `<component_name>_...()` | 同步 / 异步提交 | [返回时完成了什么] |

说明关键输出有效性、回调上下文和所有权；精确参数与错误码以公共头文件为准。

## 6. 状态、生命周期与并发

- 生命周期：[实际存在的状态和合法转换；没有生命周期时明确说明]
- 状态所有者：[唯一写入者]
- Task：[是否创建、由谁拥有、阻塞源；没有则写“本组件不创建 Task”]
- 回调/队列：[执行上下文、借用终点和队列满策略]

## 7. 故障与恢复

- [错误事实如何返回]
- [部分成功时如何回滚或保留可恢复状态]
- [哪些产品级降级、重试或重启决策明确留给 Application]

## 8. 配置与文件

- 构建配置：[相关 Kconfig、目标差异；没有则写“无”]
- 关键文件：[只解释职责不明显的文件]
- 持久化格式或兼容性：[存在时填写]

## 9. 验证

- 测试：[测试路径及覆盖的契约]
- 构建/实机检查：[与该组件风险相称的验证方法]
- 已知缺口：[尚未覆盖但不能自行补成规则的事项]
````

## 5. Application 组件附加要求

Application README 必须突出完整用例，而不是罗列下层能力：

- 写清触发条件、前置状态、调用顺序和结束条件。
- 写清输入事件如何进入、产品决策在哪里产生、结果交给谁。
- 写清网络、电源、显示、存储等共享资源由谁拥有和释放。
- 写清重试、降级、跳过、保持现状或请求重启等产品策略；未确认策略不得擅自补全。
- 如果同一 Application 内有多个子流程，必须分别说明状态所有者，避免把无关布尔状态摊平
  为一个无法归属的全局 context。

Application README 的“主要流程”应优先使用以下表达：

```text
触发事实 → Application 决策 → Service/下层执行 → 结果事实 → Application 收敛
```

## 6. Service 组件附加要求

Service README 必须说明创建该 Service 的充分理由，并明确事务边界：

- 指出它满足“跨组件固定事务”“共享资源所有权”或“复杂流程复用”中的哪一项。
- 写清事务从哪一步开始、在哪一步提交、失败时如何回滚或补偿。
- 写清 Service 自己拥有的资源和状态；没有资源所有权时不要暗示存在。
- 明确产品级触发时机、致命/降级判断和重启策略仍由 Application 决定。
- 如果存在 Task，必须解释独立阻塞源、串行化目标和同步停止终态；不能以“异步更快”作为
  唯一理由。

## 7. Agent 执行流程

创建或更新 Application/Service README 时，Agent 必须按以下顺序工作：

1. 完整阅读根 `README.md`、`docs/architecture/README.md` 及本次涉及的架构规范。
2. 检查组件 `CMakeLists.txt`、公共头文件、生命周期实现、Task 文件、测试和直接调用方；仓库
   存在 `.codegraph/` 时先使用 CodeGraph 理解调用路径。
3. 先判断组件层级和职责边界，再填写模板；不能根据目录名猜测行为。
4. 对照实现核查依赖、同步/异步语义、状态所有权、失败终态和配置开关。
5. 检查所有相对链接、组件名、API 名称和文件路径，删除模板占位文本。
6. README 与代码在同一任务中提交；最终回复说明新建或更新了哪些组件契约。

Agent 不得仅凭 README 修改公共 API，也不得为了让现有代码“符合模板”而增加空生命周期、
无意义 Service、Task 或占位抽象。

## 8. 完成检查清单

- [ ] README 位于具体 Application/Service 组件根目录，名称为 `README.md`。
- [ ] 一句话定位能够区分 Application 产品策略与 Service 技术事务。
- [ ] “负责”和“不负责”都已填写，且没有重复上层架构规范。
- [ ] 主要流程能从触发一路追踪到结果消费者。
- [ ] 依赖方向与 `CMakeLists.txt`、公共头文件和实际调用一致。
- [ ] 生命周期、唯一状态所有者、Task 和回调上下文均有明确说明。
- [ ] 失败、回滚和产品级决策边界没有混写。
- [ ] 配置、测试和已知缺口基于事实，没有自行补全未决规则。
- [ ] 公共 API、路径和相对链接有效，文档中没有遗留模板占位符。
