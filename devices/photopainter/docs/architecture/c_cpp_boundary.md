# 项目 C/C++ 语言边界规范

> 状态：已确认的全项目目标规范。本文只规定语言选择和跨语言边界，不记录当前源码清单；
> 文件增删或实现迁移不应要求同步维护一份“哪些文件是 C/C++”的列表。

## 1. 目标与适用范围

本规范适用于项目内所有层级、ESP-IDF 组件、公共头文件、私有实现、FreeRTOS Task 和回调。

语言选择必须服务于以下目标：

- 保持跨组件 API 稳定且可被 C 和 C++ 调用；
- 用最小机制表达状态、所有权和生命周期；
- 避免手工清理遗漏，同时保留可失败清理的错误语义；
- 不因语言迁移增加无业务含义的包装、继承或抽象层。

项目不按架构层强制指定语言。任何层都可以包含 C 或 C++ 实现，判断依据是代码本身的数据模型、
资源所有权和生命周期，而不是目录位置。

## 2. 默认选择规则

### 2.1 应当选择 C 的情况

满足以下特征的新增实现默认使用 C：

- 无状态或仅处理调用栈内局部状态；
- 主要工作是解析、编码、校验、换算或格式转换；
- 输入和输出可以用有界 C POD 表达；
- 只是对 C SDK、寄存器、回调或函数表做轻量适配；
- 只有少量资源，创建和释放路径短且清晰；
- 使用 C++ 不会减少所有权歧义或错误路径复杂度。

### 2.2 应当选择 C++ 的情况

满足以下任一实质条件时，应当优先使用 C++：

- 一个实例同时拥有多个需要配对释放的句柄、队列、锁、缓冲区或任务资源；
- 多个提前返回路径需要释放不同组合的已创建资源；
- 状态必须始终满足构造后不变量，普通结构体和自由函数难以保证；
- 需要创建多个彼此独立、各自拥有状态和资源的实例；
- 资源适合通过构造、析构和不可复制语义明确唯一所有权；
- 大量同一生命周期的模块级状态需要收拢为一个 Runtime。

“代码以后可能变复杂”“C++ 更现代”或“统一文件后缀”不是选择 C++ 的理由。反过来，已有 C API
也不是拒绝 C++ 私有实现的理由。

### 2.3 决策顺序

新增或实质修改实现时，按以下顺序判断：

1. 先确认公共契约、状态所有者和停止语义，不先决定语言。
2. 若代码以有界数据转换为主，选择 C。
3. 若代码以实例资源所有权和不变量为主，选择 C++。
4. 若清理可能失败或需要有界等待，保留显式生命周期 API，无论实现语言是什么。
5. 若两种语言都能同样清晰地表达，选择机制更少、与相邻私有实现更一致的一种。

## 3. 跨组件公共 ABI

跨组件公共 API 必须保持 C ABI，这是 C/C++ 混合实现的稳定边界。

- 公共头文件使用 `.h`，并能被 C 和 C++ 编译器分别包含；
- 函数声明使用 `#ifdef __cplusplus` 与 `extern "C"` 保护；
- `extern "C"` 只包围需要 C linkage 的函数和变量声明，不包围 C++ 类或标准库头文件；
- 公共签名只使用 C 标量、枚举、函数指针、C POD、不透明句柄和 `esp_err_t`；
- 公共头文件不得暴露类、模板、重载、引用、异常、智能指针或标准库容器；
- C++ 私有实现必须先包含声明该 API 的头文件，再提供定义，避免声明和定义的 linkage 不一致；
- 需要隐藏 C++ 实例时，公共 API 使用不透明句柄，并提供严格配对的创建/销毁操作；
- 不得仅为“包装 C++”增加一层无语义的转发 API，公共 C API 本身就是语言边界。

只有进程内且明确不会被其他组件、C 测试或 C 入口调用的纯私有代码，才可以使用 C++ 专用接口。

## 4. C++ 运行时约束

固件 C++ 默认不依赖异常和 RTTI。若未来确需启用，必须先评估全项目构建选项、固件体积、失败
路径和第三方库兼容性，不能由单个组件局部决定。

- 执行错误继续通过 `esp_err_t` 或公共契约规定的显式结果返回；
- 动态创建对象必须使用不会抛出异常的方式，并检查分配结果；
- 可以在私有实现中使用智能指针和标准库工具，但容量必须有界，且不得隐藏周期性无界分配；
- 禁止异常跨越公共 C API、C 回调、ISR 或 FreeRTOS Task 入口；
- Runtime 用于收拢同一生命周期的状态，不意味着必须增加接口类、继承、虚函数或机械的
  getter/setter；
- 除非确实需要运行期多态，否则优先组合和普通成员函数，不引入虚函数层级。

## 5. RAII 与可失败清理

RAII 只负责能够可靠完成、无需向调用方返回失败结果的资源释放。

适合放入析构函数的操作：

- 释放内存和局部缓冲区；
- 删除已经停止的队列、锁或信号量；
- 销毁具有明确、短时、不可失败释放契约的局部句柄；
- 回滚尚未对外发布的半构造对象。

以下操作不得只依赖析构函数：

- 需要等待 Task、DMA、网络、存储或外设达到终态；
- 可能超时、需要重试或必须返回具体错误码；
- 失败后必须保留句柄、工作状态或诊断信息；
- 只有上层策略才能决定重试、降级、复位或放弃的清理流程。

这类资源必须提供显式 `stop/deinit/close` 操作。只有操作返回成功并达到声明终态后，才能清空
状态或释放最终所有权；失败时必须保留 `STOPPING`、`CLEANUP_FAILED` 或等价显式状态并拒绝重启。

析构函数不得吞掉清理错误，也不得执行无上限等待。

## 6. FreeRTOS、ISR 与回调

- FreeRTOS 队列只按值复制 C POD 或经过验证的可平凡复制类型；
- C++ 队列元素应使用 `static_assert(std::is_trivially_copyable_v<T>)` 验证；
- 不得把含构造函数、析构函数、虚表、智能指针或标准库容器的对象直接放入队列；
- 队列消息含指针时，必须定义发送成功、队列满、取消和停止时的唯一释放责任；
- Task 入口保持 `void (*)(void *)` 兼容签名，文件后缀与 `_task.c` / `_task.cpp` 规则一致；
- ISR 和底层 C 回调需要访问对象时，使用普通静态函数或静态成员函数作为 thunk，通过 `void *ctx`
  定位实例；
- thunk 只完成参数校验、事实复制和快速投递，不在边界中执行复杂业务流程；
- 回调必须在内部状态锁之外执行，语言迁移不得改变执行上下文、借用期限和重入限制。

## 7. 文件与头文件规则

- C 实现使用 `.c`，C++ 实现使用 `.cpp`；不得通过 CMake 把 `.c` 文件强制按 C++ 编译；
- 定义 Task 入口的文件必须分别使用 `_task.c` 或 `_task.cpp`；
- 跨语言或公共头文件使用 `.h`，内容必须兼容 C；
- 只服务于同组件 C++ 私有实现的类、模板和内联工具可以放在私有 `.hpp`；
- 私有 `.hpp` 不得进入组件公共 include 路径，也不得被 C 文件包含；
- `.cpp` 可以包含 C 公共头文件；`.c` 不得依赖 C++ 私有头文件；
- CMake 必须显式列出真实源文件后缀，语言迁移时同步更新源文件列表；
- 不得为了语言分类新增 `c/`、`cpp/`、`legacy/` 等平行目录，源码仍按组件职责组织。

## 8. 迁移规则

不得为了统一语言批量迁移现有文件。单个迁移必须能指出至少一项可验证收益：

- 消除手工资源清理遗漏；
- 明确实例所有权或不可复制约束；
- 收拢同一生命周期的状态；
- 减少不安全转换或重复错误出口；
- 为多个独立实例建立清晰的对象边界。

迁移时必须：

1. 保持公共 C ABI、错误码、同步/异步语义和所有权契约不变，除非任务明确要求修改契约。
2. 保持 Task、回调、锁和队列的执行上下文不变。
3. 先处理 C++ 不允许的隐式转换、跨初始化 `goto` 和聚合初始化差异。
4. 不把自由函数机械改成类方法，不为字段机械增加 getter/setter。
5. 不把可失败停止流程塞入析构函数。
6. 更新 CMake；只有公共职责、生命周期或依赖发生变化时才更新组件 README。
7. 验证 C 调用方仍能包含头文件并链接公共符号，C++ 队列元素仍满足复制约束。

## 9. 评审检查清单

- [ ] 语言选择由数据模型和资源所有权决定，而不是统一风格；
- [ ] 公共头文件可被 C 和 C++ 分别包含；
- [ ] 公共 ABI 未泄漏任何 C++ 类型或符号重整；
- [ ] 每个句柄、缓冲区、锁、队列和 Task 都有唯一所有者；
- [ ] 队列元素是 POD 或经过可平凡复制验证；
- [ ] 析构函数没有吞掉错误或执行无上限等待；
- [ ] 可失败清理保留显式错误码和失败状态；
- [ ] C++ 实现没有依赖异常跨边界传播；
- [ ] 没有新增无语义的包装类、继承层或转发函数；
- [ ] 文件后缀、Task 命名、CMake 和私有头文件路径一致。
