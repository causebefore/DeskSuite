# 数据流、并发与 Task

## 1. 基本数据流

Application 负责完整用例编排；下层组件负责执行并报告事实：

```text
Application
    ├── 同步调用 ──→ 直接返回最终结果
    └── 异步命令 ──→ 所有者组件 ──→ 不可变完成事件
```

同步 API 返回时操作已经完成。异步 `request` API 返回值只表示命令是否成功提交，最终执行结果必须通过明确事件、结果队列或回调返回。

项目不建立全局事件总线。组件之间使用显式注册的回调、队列或 Task Notification；事件结构由生产者定义并保持不可变。

## 2. 状态所有权

- 每份可变状态、每个硬件资源只能有一个写入所有者。
- 只有所有者组件定义的串行化上下文可以修改其工作状态；组件存在专用 Task 时，只能由该 Task 修改。无 Task 的同步组件可以使用受锁保护的同步 API 或原子操作完成串行化。
- 快照必须整结构复制，不能返回内部可变指针，也不能让读取方观察到新旧字段混合。
- `volatile` 不能提供跨任务同步。必须使用队列、互斥锁、临界区、原子操作或 Task Notification。
- 状态锁只保护短时间内存操作；持状态锁期间禁止 I/O、延时、阻塞等待或调用外部回调。SPI/I²C 等完整硬件事务可以使用独立的资源锁，但范围必须有界，且不得在持有资源锁时调用外部回调或进行无上限等待。
- 回调必须在释放内部状态锁后执行，并明确执行上下文。异步事件通知回调必须快速返回，需要
  耗时处理时再次入队；同步流式处理回调可以在发起调用的上下文中执行有界工作，但不得进行
  无上限等待或重入所属组件的控制 API。以 `_borrow` 结尾的回调或 ISR handler 注册 API 可以
  借用并保存回调与上下文，直到替换、显式取消、对应 remove 或 `stop()`；调用方保证借用期内
  生命周期，ISR 必须遵守 ISR 上下文限制。
- 队列满时必须为该队列明确选择拒绝、覆盖最新值或合并重复命令，禁止静默丢弃。各队列的具体策略仍是未决事项。

## 3. Task 归属与命名

Task 是执行机制，不是架构层。项目不得建立 `components/tasks` 或同义目录。

### Device/BSP 与 Service 的执行边界

- Device/BSP 只提供同步、短时、可组合的硬件能力、状态快照和快速事件入口，不创建或持有
  长期运行的 Task、Queue、Timer。
- Driver/Device 负责硬件语义相关的状态机，例如按键去抖、协议解析和设备状态转换；状态机
  通过同步的单步推进 API 执行，不自行决定调度周期或创建执行资源。
- Service 拥有持续等待和推进状态机所需的 Task、Queue、Timer，负责周期调度、超时、重试
  退避、自动恢复和跨设备协调。产品级致命、降级、跳过或重启决策仍由 Application 拥有。
- Service 必须通过稳定 Device API 操作硬件，禁止包含 BSP、Driver 或 Board 头文件；
  Service 私有实现可以直接包含 FreeRTOS 头文件并管理 Task、Queue、Timer。

因此，按键链路应表达为“Service 定时调度 → Device/BSP 同步采样 → Driver/Device 去抖状态机
→ 不可变设备事件 → Service/Application”，而不是由 BSP 定时器直接拥有完整持续流程。

只有组件需要独立阻塞、周期调度、持续状态机或串行独占资源时才创建 Task。Task 始终留在
拥有对应流程状态和资源协调责任的 Application、Service 或 Communication 组件：

- Application Task：只汇聚通知并等待截止时间；同组件 Runtime 持有整点调度和跨组件产品状态机。
- Communication 的网络 Task：连接、断线、超时和重连状态机。
- Communication Tool 的固件 OTA Task：串行拥有目标检查、待确认目标、流式写入、镜像校验和
  启动分区切换事务；调用方拥有在线会话、按键交互和深睡策略。Task 接受写入事务后不得取消。
  构建与服务端清单提供单调 `ota_version`，服务端和设备端都只接受严格高于当前运行固件的
  目标；软件防降级不启用不可逆 eFuse，显式降级仍通过线刷完成。
- 固件检查是一次性用户意图，不是持久化运行模式。按键 Application 只上报满足时长的请求，
  电源管理 Application 负责在内容与显示收敛后取得网络会话、检查、提示、确认安装和恢复页面。
  正常内容刷新不得自动检查固件，也不得为了 OTA 周期轮询而保持在线。
- OTA 状态画面使用独立的一次性 NVS 恢复标记。
  装配层必须在显示提示前提交标记；新镜像启动后要求照片播放 Application 全屏呈现当前正常
  页面，并且只有物理刷新成功后才清除标记，失败则保留到后续成功刷新或下次启动重试。
- OTA 交互状态与普通休眠截止由同一个电源管理 Task 串行拥有。`CHECK_PENDING` 等待内容和显示
  收敛；`CHECKING`、提示页和 `INSTALLING` 统一拒绝休眠。提示页超时恢复正常页面后沿用原
  `next_refresh_at` 计划，不创建第二套刷新或唤醒时钟。
- 显示、SD 等设备流程需要耗时串行化、持续硬件事件等待或 ISR 延后处理时，由对应 Service
  创建 Task；Service 通过 Device 同步 API 执行硬件操作并拥有流程状态。
- Device 与 BSP 不得创建或管理 FreeRTOS Task。Device 只提供同步操作、状态快照和快速事件
  入口；BSP ISR 或 SDK 回调只复制事实并通知 Service Task，不执行挂载、刷新等阻塞操作。
- RTC、温湿度、PMU、SD 不因“属于外设”而各自创建 Task；没有独立阻塞源或持续流程时保持
  同步调用，不为分层形式增加 Service 或 Task。
- Main 不成为永久调度 Task。

Task 文件命名是强制规则：

- 定义 Task 入口的 C 文件必须以 `_task.c` 结尾，C++ 文件必须以 `_task.cpp` 结尾。
- Task 入口函数必须以 `_task` 结尾。
- Task 的创建、删除、`TaskHandle_t` 和主循环放在对应 `_task.c` 或 `_task.cpp` 中。
- 禁止使用 `*_worker.c`、`*_thread.c` 或 `*_loop.c` 表示 Task。
- Task 句柄、队列句柄不得出现在公共 API。
- 普通定时器或回调没有创建 Task 时，不使用 `_task.c` 后缀。
- Task 默认阻塞等待事件，不使用固定短周期轮询；默认不绑定 CPU 核，优先级和栈大小必须有测量依据。

## 4. 生命周期

只有确实存在相应阶段的组件才提供完整生命周期：

```text
UNINITIALIZED → INITIALIZED → RUNNING
       ↑             ← STOP ←
       └──── DEINIT ────────┘
```

非法状态调用返回 `ESP_ERR_INVALID_STATE`。`start()` 失败必须回滚到 `INITIALIZED`，不能留下半创建的 Task、队列或回调。简单同步组件不为形式增加空的 `start/stop/deinit`。

## 5. 产品调度与有界会话的架构边界

- Application 拥有日历时间窗口、触发提前量、截止时间、重试、跳过和降级策略；这些产品参数
  不属于通用架构规则。
- System Clock 只提供带可信状态的时间快照和校时能力。日历计算使用可信墙上时钟，清醒期间
  的截止时间和超时等待使用单调时钟，不能维护相互竞争的两套持续走时。
- Communication 只报告关联、IPv4、超时和传输结果等事实，并执行调用方发起的有界会话；
  是否开始、延长、结束或跳过会话由 Application 决定。
- Application 可以为明确的用户固件检查与确认流程临时延长在线会话；该流程必须有界，期间
  统一拒绝普通深睡。开始写入后不得取消，启动分区切换后必须立即重启。
- Storage 和 Device 只报告提交、持久化或刷新结果，不决定失败后保持现状、重试、回滚或展示
  错误页等产品策略。
- 具体的 PhotoPainter 内容刷新时段、网络会话顺序、时间校验阈值和显示收敛策略属于产品
  要求，不在通用架构规范中固定；调整这些要求不等于修改架构分层。
